About this API key generator

An API key is a password that software uses to talk to other software, and a good one has exactly the qualities a good human password has, except that nobody needs to remember it. An API key generator creates long, random strings that are hard to guess, hard to collide with, and easy to paste into a configuration file or a dashboard, all without sending anything to a server. The keys on this page are generated inside your own browser using its cryptographic random number generator, which means they never cross the network, are never logged, and cannot be recovered if you lose them, which is precisely the security property you want from a key generator.

The security of a key comes down to entropy, the number of bits of genuine unpredictability it contains. A 32-character key drawn from upper and lower case letters plus digits has about 190 bits of entropy, which is so far beyond brute-force guessing that the age of the universe is not enough time to try a meaningful fraction of the possibilities. Shorter keys, keys drawn from a small alphabet, or keys built from words and dates are all dramatically weaker, and the difference is not gradual: every additional character multiplies the search space by the alphabet size, so length is the single most powerful lever you have. This tool shows the estimated entropy for the keys it generates, so the trade-off between a key you can paste easily and a key that is genuinely strong is visible rather than guessed.

Using the tool is a matter of four choices. Set the length, with 32 characters a sensible default and 64 for high-value credentials. Set how many keys you need, since many setups want a separate key for development, staging, and production rather than one key shared everywhere. Add a prefix, such as sk- or test-, which makes keys recognisable in logs and configuration files and prevents accidental use of a test key in production. Then choose the alphabet: mixed letters and digits with symbols for maximum strength, hexadecimal for systems that expect hex, or URL-safe base64 style for keys that must survive being pasted into URLs and headers without encoding problems. The ambiguous-character option removes lookalikes like zero, capital O, and lowercase L, which matters when a human might ever need to read or type the key.

A generated key is only as safe as the habits around it, and the habits are worth stating plainly. Never commit a real key to a public repository, never paste one into a chat message or a screenshot, and never reuse one key across unrelated services, because a leak in one place then compromises everywhere else. Store keys in environment variables or a secrets manager, not in source code, and give each key the smallest permissions it needs, so that a leaked key can do limited damage. Rotate keys on a schedule and immediately after any suspected exposure, and revoke the old key rather than merely deleting it from your notes. If a key ever appears in a repository, assume it is compromised and rotate it, because automated scanners harvest exposed keys within minutes.

Prefixes and formats deserve a little more attention than they usually get, because they prevent an entire class of operational mistakes. A prefix like sk-live- versus sk-test- makes it obvious at a glance which environment a key belongs to, and many platforms use prefixes to route and validate keys before any database lookup. Hexadecimal keys are easy to validate and store, but they carry only four bits of entropy per character, so they need to be longer for the same strength. URL-safe base64 uses a larger alphabet and avoids characters that need escaping in URLs, which is why it is the default choice for tokens that travel in headers and query strings. The format option in this tool exists so the key you generate is not merely strong but also shaped correctly for the system that will consume it.

Developers often ask whether they should generate keys here or in their own backend, and the honest answer is both, for different purposes. A browser generator is ideal for creating keys to paste into a dashboard, for test and development credentials, and for one-off integrations, precisely because nothing leaves the page. A production system that issues keys to its own users should generate them server-side, store only a hashed copy, and show the key to the user exactly once, following the same pattern used by major platforms. In both cases the principles are identical: use a cryptographic random source, never a simple random function or a timestamp, make keys long, give them prefixes, scope their permissions, and plan for rotation. A key generated carelessly is worse than no key at all, because it creates an illusion of security while leaving the door effectively open.

One final caution rounds out the picture. A generated key has no value until it is stored safely, and the most common key disaster is not guessing but loss: a developer generates a key, closes the tab, and discovers that the platform will never show it again. Copy your keys immediately, paste them into your secrets store, and confirm they work before closing the page. Keep a note of which key belongs to which service, without storing the key itself in that note. Treat every key as a credential with an owner and an expiry plan, and the small discipline of generating, storing, and rotating keys properly will quietly protect every integration you build.

A worked example makes the entropy arithmetic tangible. Suppose you generate a 16-character key from lowercase letters and digits only, an alphabet of 36 characters. Its entropy is 16 times log base 2 of 36, which is about 82.7 bits, which sounds large but is within reach of a well-funded attacker with specialised hardware over a long campaign. Extend the same key to 32 characters and the entropy doubles to about 165 bits, and add uppercase letters and symbols to reach a 72-character alphabet, and 32 characters gives about 197 bits, which is beyond any conceivable brute-force search. The lesson is simple and cheap to apply: length first, alphabet second, and never a short key for anything that matters.

The worst key disasters in industry history were not caused by guessing at all, but by exposure. Keys committed to public code repositories have been harvested by automated scanners within minutes of publication, and several major breaches began with a credential found in a public repository, a shared document, or a screenshot. The defences are procedural rather than mathematical: secret scanning on repositories, short-lived keys that expire automatically, separate keys per environment so that revoking one does not halt everything, and a rotation plan rehearsed before it is needed. A generator can only give you a strong key; keeping it secret is a habit, and it is the habit, more than the algorithm, that determines whether the key actually protects anything.

A final practical note: when a platform offers to generate a key for you, prefer its built-in generator for production credentials, and use this tool for test keys, local development, and integrations where you control the secret store. Either way, copy the key immediately and confirm it works before closing the page.

Frequently asked questions

Are these API keys really random?

Yes. They are generated with the browser's cryptographic random number generator (crypto.getRandomValues), not a predictable random function, and nothing is sent to any server.

How long should an API key be?

32 characters from a mixed alphabet is a strong default (about 190 bits of entropy). Use 64 characters for high-value production credentials.

What is a key prefix for?

Prefixes like sk-live- or sk-test- make keys recognisable in logs and configs and prevent accidentally using a test key in production.

What does URL-safe base64 mean?

It uses letters, digits, hyphen, and underscore, so the key survives in URLs and headers without escaping, unlike keys containing plus, slash, or equals.

Should I store API keys in source code?

Never. Use environment variables or a secrets manager, and assume any key committed to a public repository is compromised and must be rotated.

Can I recover a key if I lose it?

No. This page does not store keys, and most platforms show a key only once. Copy keys into your secrets store immediately after generating them.
